# F05 migration, restart and readiness — PASS for `e954830`

Prepared 20 September 2026 UTC. This closes one gate for one candidate. It approves no release,
no capacity target and no production change. Production was not touched: it remained on
`d15ff395`, service active, `/api/ready` 200, with its process start time unchanged throughout.

## Method

Mirrors the exercise recorded for `ddde69a` on 14 September so the two are comparable.

The exact CI artifact for `e954830` was downloaded from remote run `35476907338`, verified against
its published SHA-256 sidecar (`b0345ac8c25c37e02e9110d5a4f6fd28a9bc30c11767771ebf1b124f0c3d95fb`)
and staged through `scripts/release_manager.py`, which validates the checksum, the embedded
`RELEASE.json` commit and archive member paths.

**The run used a virtual environment built from the artifact's own `backend/requirements.lock`,
not the development environment.** An earlier pass of this exercise used the repository `.venv`;
its results were discarded and the exercise repeated, because running a candidate under an
interpreter other than the one it pins is the same class of error recorded against production in
[`2026-09-19-deployment-divergence.md`](2026-09-19-deployment-divergence.md).

A disposable loopback-only PostgreSQL 16.4 container held the databases. No customer or production
data was used; every workspace, user and record was synthetic.

## What this does not establish

This ran on the build host against a container database. It is **not** an installed-host exercise.
It therefore does not pass `I03` (install, restart and reboot on an approved host), `S02` (isolated
staging privilege, listener, firewall and TLS evidence), `S05` (installed proxy exercise), `D03`
(owner-approved representative scale and timed RTO), `I05` (approved load targets) or `I07`
(exact-artifact deploy log from production-like staging). It does not pass `F06`, which requires a
separate staged dependency-fault exercise.

The timings above are measurements at this synthetic scale, not RTO evidence, because no owner has
approved a representative scale to measure against.

This exercise was executed by the change author. `R04` independent review and the `O05` requirement
that drills be completed by an operator other than the author both remain outstanding, and this
record is offered to that review rather than in place of it.

## Observation recorded during the exercise

`backend/app/main.py` reads `job.payload['status']` without a default while sweeping interrupted
jobs during startup. A `job` record whose payload lacks that key raises `KeyError` inside the
lifespan handler and the service exits before binding, so every worker fails to start.

This was reached with a malformed synthetic fixture, which was the author's error and not a
defect report. The API validates job payloads on write, so the state is not believed reachable in
normal operation. It is recorded because the failure mode is unhelpful if it ever is reached: the
service cannot start, and recovery would require direct database modification rather than a
restart or rollback. A default and a skip would fail soft instead.
