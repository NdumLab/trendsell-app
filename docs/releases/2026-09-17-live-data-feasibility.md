# Live-data source feasibility and access register

Prepared 17 September 2026 UTC and re-verified 18 September 2026 UTC from first-party documentation. This is a technical and
commercial feasibility review, not legal advice, a procurement approval, or permission to
collect. “Implemented” means code exists in the candidate repository. “Connected” requires a
complete server-side configuration **and a successful collection in that workspace**. “Displayed”
requires the resulting dated record to be visible to a user. Authentication alone satisfies none
of those later states.

Production currently has **zero connected live sources, zero successful live collections and zero
displayed real observations**. No fixture, demo, manual record, disabled adapter, configured key or
successful authentication changes that fact.

## Feasibility decision

The smallest plausible pilot is DataForSEO Amazon keyword/ASIN plus DataForSEO Trends, together
with a Bright Data Scraper Studio Jumia Nigeria collector. Open Exchange Rates is implemented but
is not required for the first proof because Decision Room already keeps FX as an explicit user
assumption. The pilot is not yet authorized to run: no approved accounts or secrets are installed,
Bright Data has not accepted the exact declared `jumia.com.ng` intended use, internal approvals are
pending, and no real response has been collected. Each adapter therefore requires a non-secret
reference to its applicable accepted terms/plan/intended-use basis as well as credentials. That
reference is evidence of the basis actually relied on; it does not invent a separate provider-
letter requirement where published terms already grant the use.

Amazon Creators API is not selected. Its standard license limits Product Advertising Content to the
Associates sales-referral purpose, forbids third-party/data-mining use, normally limits non-image
cache to 24 hours, and ties continuing quota to referred sales. That conflicts with a durable,
multi-source commercial research record without a written exception.

## Usage-basis record and genuinely open questions

Before enablement, Procurement/Privacy must record which published terms, ordered plan and declared
intended use establish each use. `*_USAGE_RIGHTS` holds that non-secret reference; credentials never
do. It is not proof of collection and it is not a demand for a bespoke letter where applicable terms
already grant the intended use.

- **DataForSEO:** the current own-product/white-label statement establishes normalized display in
  TrendSell’s tools, dashboards and client deliverables, including derived presentation. Record the
  accepted 12 June 2026 terms/product-page versions and internal 30-day policy. No additional written
  permission is presently identified for the narrowed, image-free pilot.
- **Bright Data:** the published agreement establishes public-data collection/delivery and prohibits
  distribution only when used to offer a similar/competitive data service. Submit the exact
  `jumia.com.ng` fields, invite-only normalized display, derived analysis and 30-day policy through
  Bright Data’s intended-use/KYC process. The open decision is acceptance of that declared use and
  the upstream Jumia/rightsholder analysis—not a generic request to restate already published terms.
- **Open Exchange Rates:** the service agreement establishes reasonable licensed use and the ETag
  documentation expressly permits whole-response caching. Record the accepted plan/terms. Clarify
  only if TrendSell will profit directly from providing the rates or redistribute raw rate data.

Images remain excluded from this candidate. Full raw provider responses are hashed in memory and
discarded; only normalized, field-limited snapshots are retained. The configured 30-day
DataForSEO/Bright Data windows and 365-day OXR window are internal policies, not claimed provider
mandates. Expiry deletes live evidence/snapshots and dependent product fields, while historical
assessments keep their economics and an evidence tombstone with provider values removed. Encrypted
backup copies age out under the backup lifecycle; any restore applies provider expiry before serving
authenticated data.
